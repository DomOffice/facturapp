### Réseau PROD

NetBird est utilisé comme réseau principal testé :

```text
PROD NetBird : 100.92.8.37
DEV NetBird  : 100.92.240.170
interface    : wt0
```

WireGuard est conservé comme secours :

```text
PROD WireGuard : 10.8.0.1
```

Diagnostic Windows effectué :

- `wt0` était classée `Public` ;
- les règles Windows `Node.js JavaScript Runtime` et `python.exe` bloquaient les connexions entrantes Public ;
- le passage de `wt0` en `Private` a rendu TCP/3001 et TCP/3306 accessibles avec le pare-feu actif.

Ne pas supprimer WireGuard tant que le scénario de secours n'est pas définitivement documenté/testé.

Point à confirmer sur PROD : valeur finale de `NEXTAUTH_URL`. Si elle vaut encore `http://10.8.0.1:3001`, l'accès NetBird peut rediriger vers WireGuard. La cible principale souhaitée est NetBird, mais une solution par hostname/DNS interne serait plus robuste pour un vrai failover.

### Copie PROD → DEV

Procédure validée pour obtenir une copie fidèle de PostgreSQL PROD :

1. `pg_dump` sur PROD ;
2. copie du `.dump` sur DEV ;
3. suppression/recréation de `facturapp_db` DEV ;
4. `pg_restore` ;
5. tests FacturApp.

PostgreSQL 18 est installé et les outils sont disponibles sous :

```text
C:\Program Files\PostgreSQL\18\bin\
```

### MariaDB annuelle

Décision d'architecture :

```text
erp2025
erp2026
erp2027
...
```

sont des bases annuelles indépendantes.

PostgreSQL `facturapp_db` doit être consolidé multi-années.

La V2 `prisma/sync-mariadb-to-pg.ts` est désormais préparée pour importer une année avec `SYNC_YEAR` sans collision d'IDs transactionnels et sans `DELETE FROM paiements` global.

La V2 symétrique `scripts/sync-pg-to-mariadb.ts` reste à développer/tester afin que chaque exercice PostgreSQL soit envoyé uniquement dans `erpYYYY`.
